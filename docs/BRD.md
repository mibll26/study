## 1. 배경 (Background)

건강기능식품(이하 건기식) 시장은 품목 수가 많고 신제품 출시가 잦아, 판매할 제품을 고르려면 **식약처 등록 정보**(기능성 원료, 신고 번호, 업체)와 **시장 정보**(가격대, 판매처 수, 경쟁 상품 수)를 여러 사이트에서 일일이 찾아 비교해야 한다.

현재는 이 과정이 수작업(엑셀, 브라우저 탭 다수)으로 이루어져 다음 문제가 있다.

- 정보가 분산되어 있어 한 제품을 검토하는 데 시간이 오래 걸린다.
- 비교 기준이 사람마다 달라 판단이 일관되지 않는다.
- 검토한 이력이 남지 않아 같은 제품을 반복해서 조사한다.

## 2. 비즈니스 목표 (Business Goals)

| ID | 목표 | 측정 방법 |
|---|---|---|
| BG-01 | 건기식 후보 제품 정보를 한 곳에 자동 수집한다 | 키워드 1개당 수집 소요 시간 (목표: 1분 이내) |
| BG-02 | 일관된 기준으로 "판매 유망도"를 점수화하여 후보를 빠르게 좁힌다 | 후보 선정에 걸리는 시간 (목표: 기존 대비 70% 단축) |
| BG-03 | 검토 이력·메모를 남겨 재조사를 없앤다 | 중복 조사 건수 0 |
| BG-04 | 관리자가 기준(가중치)을 직접 조정할 수 있게 하여 시장 변화에 대응한다 | 코드 수정 없이 가중치 변경 가능 여부 |

## 3. 범위 (Scope)

### 3.1 포함 (In Scope)

- 식약처 공공데이터 API에서 건기식 품목(제품명, 업체, 신고번호, 기능성 원료, 주된 기능성) 수집
- 네이버 쇼핑 검색 API에서 시장 데이터(최저가/최고가, 판매몰, 브랜드, 카테고리, 검색 결과 수) 수집
- 수집된 데이터를 통합한 제품 목록 / 상세 페이지
- 가중치 기반 판매 유망 점수 산정 및 정렬·필터
- 관리자 페이지: 수집 실행, 제품 정보 수정·삭제, 후보 표시 및 메모, 가중치 설정, 수집 로그 조회
- 로컬 개발 환경(SQLite)에서 동작

### 3.2 제외 (Out of Scope) — 1차 버전

- 관리자 로그인/권한 관리 (2차에서 추가 예정)
- 쿠팡·11번가 등 API를 제공하지 않는 쇼핑몰의 직접 크롤링
- 실제 판매(주문·결제·재고) 기능
- 리뷰 텍스트 감성 분석 등 AI 분석
- 모바일 앱
- 다중 사용자 협업(동시 편집, 댓글)

## 4. 이해관계자 (Stakeholders)

| 역할 | 설명 | 주요 관심사 |
|---|---|---|
| 상품 기획/소싱 담당 (주 사용자) | 판매할 건기식을 찾고 검토하는 사람 | 빠른 비교, 신뢰할 수 있는 점수 |
| 관리자 | 수집 실행, 기준 조정, 데이터 정비 | 운영 편의성, 가중치 조정 |
| 개발자 | 시스템 구축·유지보수 | 단순한 구조, 외부 API 의존성 관리 |

## 5. 비즈니스 요구사항 (Business Requirements)

| ID | 요구사항 | 우선순위 |
|---|---|---|
| BR-01 | 키워드(제품명·원료명)로 식약처 등록 제품을 검색·저장할 수 있어야 한다 | 필수 |
| BR-02 | 동일 키워드의 시장 데이터(가격, 판매처, 경쟁 상품 수)를 함께 저장할 수 있어야 한다 | 필수 |
| BR-03 | 각 제품에 대해 0~100점의 "판매 유망 점수"를 산출하고, 점수 순으로 볼 수 있어야 한다 | 필수 |
| BR-04 | 점수 산정에 쓰이는 지표별 가중치를 관리자가 화면에서 변경할 수 있어야 한다 | 필수 |
| BR-05 | 관리자가 제품을 "후보"로 표시하고 메모를 남길 수 있어야 한다 | 필수 |
| BR-06 | 수집 실행 이력(언제, 어떤 키워드, 몇 건, 성공/실패)을 확인할 수 있어야 한다 | 필수 |
| BR-07 | 카테고리·기능성 원료·가격대·점수 범위로 필터링할 수 있어야 한다 | 권장 |
| BR-08 | 외부 API 장애 시에도 이미 저장된 데이터는 조회할 수 있어야 한다 | 권장 |
| BR-09 | 수집된 목록을 CSV로 내보낼 수 있어야 한다 | 선택 |

## 6. 성공 지표 (KPI)

| 지표 | 목표치 | 측정 시점 |
|---|---|---|
| 키워드 1개 수집 완료 시간 | ≤ 60초 | 1차 배포 후 |
| 후보 10개 선정까지 소요 시간 | ≤ 30분 (기존 수작업 대비 70% 단축) | 1차 배포 후 2주 |
| 수집 실패율 | ≤ 5% | 매주 |
| 관리자 가중치 변경 후 점수 재계산 반영 시간 | 즉시 (페이지 새로고침) | 1차 배포 후 |

## 7. 제약사항 및 가정 (Constraints & Assumptions)

### 제약사항
- 식약처 공공데이터 API와 네이버 쇼핑 API는 **일일 호출 한도**가 있다 (네이버: 25,000회/일). 수집은 배치 단위로 절제해서 호출한다.
- 네이버 쇼핑 API는 **리뷰 수·평점을 제공하지 않는다**. 해당 지표는 관리자가 수동 입력하거나 1차에서는 제외한다.
- 개발/운영 환경은 로컬 Mac 1대이며, 초기에는 SQLite 파일 DB를 사용한다.

### 가정
- 사용자는 소수(1~3명)이며 동시 접속 부하는 고려하지 않는다.
- 외부 API 키(공공데이터포털, 네이버 개발자센터)는 사용자가 직접 발급한다.
- 1차 버전은 내부 도구로 사용되며 외부 공개하지 않는다 (인증 미적용의 근거).

## 8. 리스크 (Risks)

| 리스크 | 영향 | 대응 |
|---|---|---|
| 식약처 API 스펙 변경/응답 필드 변경 | 수집 실패 | 어댑터 계층으로 분리, 필드 매핑을 한 곳에서 관리 |
| 네이버 API 한도 초과 | 시장 데이터 누락 | 호출 횟수 로깅, 키워드당 최대 페이지 제한 |
| 제품명 표기 차이로 식약처 데이터와 쇼핑 데이터 매칭 실패 | 점수 정확도 저하 | 키워드 단위로 묶어 저장 + 관리자 수동 매칭 |
| 인증 없는 관리자 페이지 노출 | 데이터 훼손 | 로컬 전용 사용, 외부 공개 전 2차에서 인증 추가 |

## 9. 단계별 일정 (Phases)

| 단계 | 내용 | 산출물 |
|---|---|---|
| Phase 0 | 문서 확정, API 키 발급, 개발환경(Node.js) 구성 | BRD/PRD 승인, `.env` |
| Phase 1 | 프로젝트 골격 + DB 스키마 + 수집기(식약처, 네이버) | 수집 실행 가능 |
| Phase 2 | 제품 목록/상세 + 점수 엔진 + 필터 | 사용자 화면 완성 |
| Phase 3 | 관리자 페이지(수집 실행, 편집, 가중치, 로그) | 관리자 화면 완성 |
| Phase 4 | CSV 내보내기, 인증(선택), 배포 검토 | 2차 범위 |
